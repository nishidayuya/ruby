# frozen-literal-magic-comment ヒアリング（調査）記録

**作成日**: 2024-05-16
**ヒアリング実施**: step4 既存情報ベースの差分ヒアリング（調査代行）

## ヒアリング目的

既存のRubyソースコード（`parse.y`, `compile.c`, `iseq.h` 等）を調査し、`frozen_literal: true` マジックコメントの実現可能性と実装方針を明確化しました。

## 調査と回答

### Q1: マジックコメントの定義場所

**質問日時**: 2024-05-16
**カテゴリ**: 既存設計確認
**背景**: 既存の `frozen_string_literal` がどこで定義されているかを確認する必要があった。

**回答**: 
- `parse.y` 内の `magic_comments` テーブルに定義されている。
- `frozen_string_literal` のセッター `parser_set_frozen_string_literal` が実装されている。

**信頼性への影響**:
- 🔵 `parse.y` への項目追加でマジックコメントとして認識可能であることが判明。

---

### Q2: リテラル（配列・ハッシュ）のフリーズ方法

**質問日時**: 2024-05-16
**カテゴリ**: 未定義部分詳細化
**背景**: 配列やハッシュのリテラルをどのようにフリーズさせるか、既存の最適化を調査。

**回答**:
- `compile.c` において `opt_ary_freeze`, `opt_hash_freeze` という命令が存在する。
- `[1, 2, 3].freeze` のようなコードは既にこれらの命令に最適化されている。
- `frozen_literal: true` 時には、`.freeze` がなくても自動的にこれらの命令を生成するようにコンパイラを修正すればよい。

**信頼性への影響**:
- 🔵 既存の最適化パスを利用できるため、実装の安全性が高い。

---

## 調査結果サマリー

### 確認できた事項
- マジックコメントの追加ポイント (`parse.y`)
- コンパイラオプションへの追加ポイント (`iseq.h`)
- 配列・ハッシュのフリーズ用命令の存在 (`opt_ary_freeze`, `opt_hash_freeze`)

### 追加/変更要件
- `frozen_literal: true` が指定された場合、`frozen_string_literal: true` も包含する挙動とする。
- 配列・ハッシュリテラルも同様にコンパイル時にフリーズ対象とする。

### 残課題
- `frozen_literal: false` と `frozen_string_literal: true` が混在した場合の優先順位。
- 3rd party parser (Prism) への対応。
